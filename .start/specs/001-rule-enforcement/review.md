### AC → EARS traceability

- [advisory] Soft-rule failure on the prompt point has no EARS criterion. The PRD FR-9 assumption says soft rules fail open and AC-9.2 says a failed warn check is reported to the user. The Check points table says a prompt check with only warn rules fails open, and Runtime says the user is told. Behavior FR-9 has an EARS only for a warn check on a tool call (the 'IF the check of a warn rule fails, THEN ... let the call proceed' line). None covers a failed warn check as the user submits a prompt. — SDD Behavior > FR-9 fail-safe; Components > Check points table (prompt row) → Add: IF the check of a warn rule on prompt fails, THEN THE SYSTEM SHALL send the prompt and tell the user the check failed. Trace it to AC-9.2 and the FR-9 assumption.
- [advisory] Rule-format behaviors are specified under Interfaces but have no EARS and no PRD basis. (a) An empty body loads with a warning and a default message. (b) A warning when the body names no allowed alternative. (c) Two same-name files in one folder keep the first by file name and mark the rest invalid. (d) The `tool_matcher` field is added to the format, but PRD FR-1 does not list it as a rule field. These are not in the PRD's acceptance criteria. (b) is a design mechanism for NFR-9, not an AC. (c) is an AC-1.2 sub-case that is never stated as EARS. — SDD Interfaces & data > Rule format > Validation; Rule sources responsibility (duplicate names); rule-format YAML (`tool_matcher`) → Add EARS lines tracing (a)-(c) to AC-1.2 and NFR-9, or drop the behavior. State that `tool_matcher` is Hookify's own field, covered by AC-1.4, and add an EARS line for it if it is kept.
- [advisory] The EARS for the local log contradict the findings-in-log criteria. The EARS and the Event log row say the log holds no file content, prompt text or command text. The row lists only rule name, outcome, event, tool and target. Yet the EARS say that with no surface, evaluator findings are recorded in the session log only (the FR-8 assumption). The finding text is then unreadable to the user. PRD DR-6 also classifies the log as 'may quote code and commands', and the design is narrower than that. — SDD Behavior > FR-8 (log lines); Plugin local state > Event log → Decide whether the log carries the finding text, capped at 300 characters. If it does, update the Event log row and the EARS, and keep the DR-6 sensitivity note. If it does not, change the no-surface EARS to say the finding is counted but not readable.

### MECE (boundaries)

- [advisory] Check is the sole writer of the in-flight record, and the record is 'cleared when next settles or the call is denied'. Only `markPassed` is exposed, and it is called before `next`. No component is assigned the clear when `next` settles. Gate and Prompt guard cannot clear a record they do not own. Check never sees `next` settle. The after-call run by the Reviewer is also unspecified: it is not stated whether it creates a record, and a record there would wrongly arm the backstop. — Components: Check (in-flight record) vs Gate and Prompt guard; Plugin local state: In-flight check record → Add `settle(key)` to Check's interface, called by Gate and Prompt guard in a `finally` around `next` and on deny. State that Check's after-call, stop and warn-only runs write no in-flight record.
- [advisory] Two components act on the same `classic.SubagentStop` event, the Turn guard for stop rules and the Reviewer for queue draining. Neither Mod entry's wiring nor any interface says who owns the handler, in what order they run, or how the Reviewer's drain stays off the Turn guard's block/pass return value. This leaves an unowned seam on one event. — Components: Reviewer ('at an agent's own classic.SubagentStop ... drains that agent's queue') and Turn guard (classic.SubagentStop); Mod entry → State that Mod entry registers one `classic.SubagentStop` handler. It calls the Reviewer's `drain(agentId)` as a side effect, then returns the Turn guard's result. The Reviewer's drain must never affect that return value.
- [advisory] Rules claims to be the sole owner of message wording, but other user-facing text has no owner. This includes the loop-guard-override notice 'which rule kept blocking', the Hookify double-enforcement notice, the 'rule rejected' text, the 'review failed' and 'not reviewed' notices, and the warn check-failed notice. Wording is spread across Recorder, Check and Mod entry without being assigned, which risks drift against AC-8.3 labelling. — Components intro and Rules ('`checkFailedMessage` and `findingMessage`, the only other message wording'); Recorder, Control commands, Check → Either assign all user-facing notice wording to Recorder, keyed by Event.kind, and limit Rules to Claude-facing messages, or extend Rules with a `noticeText(kind, ...)` function. Narrow the 'only message wording' claim accordingly.
- [advisory] The diagram draws a Turn guard to Recorder edge. The intro says the Turn guard reports only 'events Check cannot see', but the Turn guard row names no event it reports. Check reports every stop outcome, including the override. The edge is therefore a duplicate or stale consumer-to-provider path. — Components diagram and Recorder reporting: 'Check & Reviewer & TurnGuard & Sources --> Recorder' vs the Turn guard row and the intro sentence → Remove the TurnGuard to Recorder edge, or name the specific event the Turn guard reports. Also correct the intro to list only Reviewer, Rule sources and Mod entry as direct reporters.
- [advisory] CheckResult restates `resolve`'s return type `{action, rules, message, failures}` by reference ('resolved fields') and adds `deferred`. The Check to guard interface is therefore undefined, and the same datum risks two shapes. The failure-policy fold, a failed hard rule becoming `block`, is applied by both `resolve` and Check, so the owner of that fold is ambiguous. — Entities: CheckResult ('resolved fields, plus deferred') vs Selection.resolve output → Define CheckResult explicitly as `{ action, rules, message, deferred }`. State that `resolve` produces failures and a block message for failed hard rules, and that Check only decides which verdicts count as failed. Alternatively state that Check applies the fold, and drop it from `resolve`.
- [advisory] (unverified) The rule format has two sources of truth: Rules in code and the Drafting skill's prose. The parity test narrows the gap but does not remove it. Rule files the skill writes also bypass Rules' validation until the next load. This is acknowledged for AC-1.2 but is a genuine duplicate of format knowledge. — Components: Drafting skill and Rules (rule format); Data ownership → Keep the parity test as a required CI gate. Optionally have the skill call a validating command, such as a `/cc-enforcer-validate <path>` Control command backed by Rules, before approval, so the format has one owner at run time.

### Design risk

- [blocking] robustness: The two parts of the design disagree. The backstop denies when no record exists, and it passes an error from `next` through only while the phase is `passed`. But the record is cleared when `next` settles, and that includes a rejection. If a later mod or Claude Code itself makes `next` reject, the clear runs first as the error unwinds through the handler. The `.catch` handler then finds no record and denies a call that already ran or may have run. Claude is told the edit or command was blocked when it actually happened, so it may retry or reason from wrong state. This breaks the stated rule that the backstop never denies once the phase is `passed`. — Plugin local state > In-flight check record ("cleared when `next` settles") vs Runtime > Before a tool call, step 5 (Backstop) → Clear the record only after `next` resolves successfully. On rejection, leave a `passed` tombstone that the backstop consumes and clears. Also state in Check's `backstop` contract that 'no record' means 'never reached markPassed', which needs a separate set of tool-use ids already marked passed for this session. Add an eval case where a later mod throws after `next`, and assert the result is a pass-through and not a deny.
- [blocking] robustness: The project folder is defined as the nearest `.claude/` that holds `hookify.*.local.md`, and that choice is cached for each working directory. In a project with no rule files yet, the search finds nothing (or an upper folder), and the result is cached. When the Drafting skill then saves the first project rule into `<cwd>/.claude/`, or the user adds one or checks out a branch that has one, that folder is never chosen again. The new rule is ignored for the rest of the session. This breaks AC-12.2 ('applies to the next tool call'), AC-3.1, and the NFR-13 zero-config first-rule flow. — Components > Rule sources (`current()`: project folder 'resolved once per working directory and cached') and Interfaces & data > Project folder → Cache only the candidate directory chain (working directory up to the git root), not the chosen folder. On each `current()`, choose the nearest candidate that holds rule files from the listings it already takes, or list every candidate and fingerprint the choice. As a minimum, make the drafting-skill write and FR-3 add/delete invalidate the cache. Add an eval: an empty project, then a draft is approved, and the next tool call is checked against it.
- [advisory] robustness: All listing errors are handled the same way. A project `.claude/` folder that was deleted or moved (for example `rm -rf .claude`, or switching to a branch without it) fails `$.fs.list`. It is then treated as unchanged, so every rule in it keeps enforcing even though the files are gone. This contradicts AC-3.1 (deleted rule files stop applying on the next call). — Components > Rule sources ('a folder that cannot be listed counts as unchanged') → Treat 'not found' as an empty folder: drop its rules and record the change. Keep 'unchanged plus report once' only for other I/O errors, such as permission errors or transient failures.
- [advisory] (unverified) robustness: Each agent's queue holds up to 50 entries with up to 4 KB of content each. A queue is emptied only at that agent's `turn.complete` or `classic.SubagentStop`, or, for the main session, at `prompt.submit`. Workflow-tool and background agents with unlisted `agentId`s may never send either event to the mod. Their queues then stay in `$.state` for the whole session, with no limit on how many there are, and their entries are never reported as not reviewed. — Plugin local state > Review queue ('per agent', at most 50 entries); Components > Reviewer → Put a session-wide limit on the number of queued agents or on total entries. Also drain, and report as not reviewed, any agent queue that has not changed for a set time or at `session.end`, if that event exists.
- [advisory] (unverified) robustness: The read-then-fill sequence is not atomic and has no retry limit. A user who keeps typing can make it loop with no end. A keystroke between the final read and `fill({mode: 'replace'})` is still lost. On a surface without a prompt box, `$.prompt.submit` fires `prompt.submit`. That runs `reset()` (main queue reported as not reviewed) and the prompt rules over the findings text, so a `block` prompt rule can drop the findings the user chose to send. — Runtime > After a tool call, step 5 ('Send to Claude': read, re-read, 'starting over if the text changed') → Limit the re-read loop to a few tries, then show 'prompt changed, press again'. Use an append mode if `$.prompt.fill` supports one. Mark submissions that cc-enforcer starts so that the Prompt guard and `reset()` skip them, or say in the design that findings are subject to prompt rules.
- [advisory] (unverified) compatibility: cc-enforcer-only rules are written into Hookify's own file names, in a project folder that is committed and shared. Teammates who run only Hookify will load them. It is still an open question whether Hookify treats an unknown action as `warn`/`block`, or skips an unknown operator in a way that makes the other conditions decide alone. If it does, a shared `block`+`llm_evaluate` rule would fire on its matchers alone for those teammates. The design's only answer is documentation, and the file-naming choice is hard to change once users have written files. — Boundaries > Must preserve (Hookify does not understand `ask`/`llm_evaluate`); Open questions row 'What does Hookify do with `action: ask` and an `llm_evaluate` condition?'; ADR-5 → Answer the open question from `core/rule_engine.py` before release. If Hookify would make a rule stronger (fire on matchers alone, or treat `ask` as `block`), the Drafting skill and validation should warn on such project rules, or the format should use a guard Hookify ignores safely (for example a condition Hookify never matches). Record the outcome in ADR-6.

## How to act

The design is human-owned. Resolve each blocking finding with the user, and confirm any architecture decision it touches (both blocking findings are under Design risk: the in-flight record clear vs backstop ordering, and the cached project-folder choice). Then re-run the review. Advisory findings may ship with a note.

## Disposition (2026-10-12)

Both blocking findings of this round were fixed in solution.md (the in-flight record survives a rejected `next`; the project folder is re-chosen on every `current()`), along with the deleted-folder advisory. The user approved the design without a further round; the remaining advisory findings above ship as known notes for the plan.
